## Решения

### 1. Хранилище — свой файл рядом с `command.json`

`~/Library/Application Support/MyClaude/window-themes.json`. Формат зеркалит карту страницы:

```json
{"version":1,"at":"2026-09-06T01:20:00Z","entries":{
  "id:local_ab12":{"theme":{"id":"ocean","name":"Океан","type":"dark","palette":{"accent":"#…","background":"#…","foreground":"#…","sidebar":"#…","panel":"#…","muted":"#…"}},"font":{"id":"menlo","family":"Menlo","mono":true},"size":{"answer":16},"frame":true,"at":1757100000000},
  "chat:Trelvis":{"theme":{"…":"…"},"at":1757100000000},
  "main":{"…":"…"},
  "*":{"font":{"…":"…"},"at":1757100000000}
}}
```

- Порядок полей записи — **`theme, font, size, frame, at`** (как `layerFields`, `ClaudeActions.swift:409`).
- Слой-сброс пишется строкой `"none"` — страница её уже понимает (`themeEntry` `:858`), и «Как у Claude»
  переживает переустановку наравне с цветом.
- Палитра — **целиком**: id темы недостаточно (каталог и `my-themes.json` могут смениться, п. 22).
- `at` — миллисекунды, по нему вытесняем.
- **Потолок один и он байтовый: 32 КБ** тела будущей команды `themes-restore` (тот же потолок, что у сводки,
  п. 23: `StatusFeed.totalLimit`, `StatusFeed.swift:25`). Вытеснение — по `at`, самое старое первым, пока не влезет.
  Счётчика «120 ключей» **нет**: полная запись (палитра из шести цветов + шрифт + обе половины размера + рамка + `at`)
  весит ≈ 360 байт, 120 × 360 ≈ 43 КБ — два потолка противоречили бы друг другу. Второй, страховочный, потолок —
  **200 ключей**, ровно столько же принимает страница (решение 4): он не рабочий, а от порчи файла.
- Поле `pos` в записи **зарезервировано** под позиции окон и в WF35 никем не пишется и не читается (решение 10).

Почему файл, а не UserDefaults: Элвис просил «хранить в Пимпе на диске»; файл виден глазами и на гейте;
`ThemeStore` держит только id и ключуется AX-заголовком (п. 22). UserDefaults остаётся тем, чем был, — памятью галок.

### 2. Что попадает в файл при записи

Каждая **закрепляющая** (не примерочная) команда `theme`, которую пишет приложение: меню, «Своя тема…»,
«Раскрасить по кругу», «Как у Claude (все окна)», цвет проекта. Точек **три** (п. 15), и чтобы зеркало не
разъехалось, ставится оно **одной приватной функцией**:

```swift
private func recordTheme(fields: [(key: String, value: CommandValue)])   // ClaudeActions
```

— она сама разбирает `scope`/`title`/`match`/`chat`/слои из тех же полей, что ушли в команду, и зовёт
`WindowThemeStore`. Вызов ровно в трёх местах, сразу после успешного `commands.write(action: "theme", …)`:
`applyTheme` (`:370`), **`paint` (`:677`, «Раскрасить по кругу»)**, `applyProject` (`:827`). Четвёртое место —
`sendPreview` (`:616`) — не зовёт её **никогда**: примерка это экран, а не выбор.
`live-colors` не пишется: у крутежа своя память (`LiveColorsStore`) и своя досылка.

Дыра, названная честно: **`new-window` (WF16) тоже несёт слои** `theme/font/size/frame`
(`ClaudeActions.swift:204`, `layerFields` `:409`) и закрепляет тему нового чата — в зеркале его нет,
потому что в момент команды id и заголовок будущего окна ещё не существуют. Затягивает её ответ probe
(решение 3): на ближайшем круге карта страницы придёт уже с этой записью. Батчу V это **не находка**.

Ключ берётся из полей той же команды — второй реализации `writeKeys` в Swift нет (п. 29):

| Что в команде | Ключ(и) в файле |
|---|---|
| `scope:"all"` | `*`, и у всех остальных записей этот слой снимается (как делает страница, п. 11) |
| `scope:"window"` + `chat:"local_…"` (WF29) | `id:local_…`; плюс `main`, если это главное окно; плюс тень `chat:<заголовок>`, если заголовок не заглушка |
| `scope:"window"` + `match` без `chat` (главное окно, id неизвестен) | `main` + тень `chat:<заголовок>`, если он не заглушка |
| `scope:"window"`, обычный заголовок, id неизвестен | `chat:<заголовок>` |
| `scope:"window"`, заголовок-заглушка, id неизвестен | `main`, если окно главное; иначе не пишем ничего |
| заголовок пустой (адресация фокусом) | не пишем ничего — какое окно, неизвестно |

Тень `chat:<заголовок>` нужна окну, которое своего id ещё не знает (попап в первые секунды, п. 26).
Цена ошибки в ключе — окно вернётся серым, а не чужого цвета: возврат доливает только пустые слои (решение 4).

### 3. Файл догоняет правду через probe WF29 — и это заменяет бутстрап

`ChatProbe` (п. 28) и так спрашивает страницы своим скриптом. Добавляем к его ответу **одно поле**:
`themes` — разобранный `localStorage["myclaude-themes-v1"]` (лишнего круга ответов не появляется).

**Кто отдаёт `themes`.** Только страница, у которой `themable && isMainWindow()` (`inject.js:800`, `:804`).
Причина — п. 28а: лоадер гоняет `probe.js` во всех страницах подряд, карта тем на origin одна, и без этого
условия каждая страница вернула бы её КОПИЮ (ответ и так 3,9 МБ), а страница-артефакт на чужом origin вернула бы
**пустую** карту и подсунула ложный вход правилу ниже. `ChatProbe` вдобавок принимает поле `themes` только
из ответа, чей `url` начинается на `https://claude.ai/`; попапы (`about:blank`) поле не шлют вовсе.

**Правило слияния.** Карта страницы не пуста → она **целиком** становится `entries` файла (страница —
источник правды: там и то, что Элвис выбирал до этого воркфлоу, и то, что он снял руками).

Пустая карта — единственное место, где нужен нюанс, и он не про удобство, а про потерю данных:

- **первый ответ probe в поколении** (сразу после старта приложения или смены pid Claude) пустой →
  **файл не трогаем**: это и есть переустановка, терять нечего, возвращать есть что;
- **любой более поздний пустой ответ в том же поколении** → **`entries` файла очищаются**: пусто на живом
  Claude значит «Элвис снял всё сам».

Почему нельзя было оставить «пусто → файл не трогаем» всегда (проверено по коду, находка критика):
«Как у Claude (все окна)» доходит до **полностью пустой карты за два клика**. `runThemeCommand` при
`scope:"all"` делает `delete entry[layer]` у ВСЕХ записей и выбрасывает опустевшие (`inject.js:1334-1351`),
а `writeThemeMap` на пустой карте делает `localStorage.removeItem` (`:838-843`). Маркер `"none"` тут не
спасает: его ставит только `setMapLayers` и только если у слоя есть запись `*` (`:1147`), а `scope:"all"`
с `theme:null` этот самый `*`-слой и удаляет. То есть у карты, где кроме тем ничего нет,
`autoPaintReset` (`ClaudeActions.swift:650`) оставляет **ноль ключей** — и старое правило вернуло бы снятые
цвета на следующем поколении. Понятие поколения уже введено решением 5, второй механики не заводим.

Почему так, а не «доливать в файл»: если файл только пополнять, снятый слой («Как у Claude» через `scope:"all"`,
п. 11) останется в файле навсегда и воскреснет при следующем возврате. А замена целиком самолечится: любая
ошибка зеркала (решение 2) исправляется первым же ответом страницы.

**Бутстрапа из UserDefaults не делаем** — это решение его закрывает: пять окон Элвиса прямо сейчас держат свои темы
в localStorage, и файл наполнится ими на первом же ответе probe, с настоящими палитрами и настоящими ключами.
UserDefaults дал бы только id и заголовки (п. 22).

**Четвёртая причина опроса — «мы только что писали зеркало».** Сегодня `ChatProbe` спрашивает страницы только
по причине (п. 28б), а выбор темы причиной не является: без этой строки файл догонял бы правду ТОЛЬКО зеркалом
решения 2, и все обещания про самолечение были бы пустыми. Поэтому `recordTheme` поднимает у `ChatProbe` разовый
флаг, и ближайший тик (с обычным зазором ≥ 5 с) спрашивает страницы. Флаг снимается опросом, шторма не будет.

Что остаётся ограничением, названным честно: ответ probe отражает карту на момент СНЯТИЯ, а кладётся в файл
через круг (~2 с). Выбор темы ровно в этом окне откатит файл на один шаг — и будет исправлен следующим же
ответом (флаг выше как раз его и заказывает). Страница при этом не страдает: возврат доливает только пустые слои.

### 4. Возврат — одна команда, слияние по слоям; страницу «ты пуста?» НЕ спрашиваем

(Пустоту приложение всё-таки различает — но по СВОЕМУ ответу probe и только в решении 3. Здесь речь о том,
что перед возвратом никакого отдельного вопроса странице не задаётся: слияние по слоям делает его ненужным.)

Контракт (побайтно, порядок полей):

```
{"id","action":"themes-restore","at","scope":"all","entries":{<ключ>:{theme?,font?,size?,frame?}}}
```

`at` внутри записей в команду **не идёт** — странице он не нужен, он бухгалтерия файла.

Страница (`runThemesRestoreCommand`): работает только если `themable` (`:800`); проверяет ключ (`*`, `main`,
`chat:…`, `id:…`, `w:…`, не длиннее 200 знаков), гонит запись через `themeEntry`/`LAYER_NORMALIZE`, мусор
отбрасывает, принимает не больше 200 ключей — и **доливает недостающие СЛОИ**: для каждого ключа и каждого из
четырёх слоёв, если слоя в карте страницы нет, берёт его из команды; всё, что у страницы есть, не трогает вовсе.
Потом `restoreTheme(false)` — покрасить тем, что нашлось, ничего не снимая.

Почему слияние, а не «спросить страницу, пуста ли память» (прямой вопрос задания):

- **Слияние идемпотентно.** Память цела — все слои на месте — команда не меняет ни байта и ничего не перекрашивает.
  Значит знать, пуста память или нет, не нужно вовсе: это и есть ответ на «как страница скажет, что забыла».
- **Отдельный probe под это заводить нельзя.** Канал один, он уже поделён по правилам WF29 (уступает агенту на
  гейте), и круг ответа — 2 с. Вопрос «ты пуста?» стоил бы столько же, сколько сам возврат, и мог бы не получить
  ответа вовсе.
- **Одна команда вместо N.** Досылка по окнам (0,6 с на запись) вернула бы только те чаты, что открыты сейчас;
  общая карта возвращает и `*`, и `main`, и записи чатов, которые Элвис откроет позже, — они лягут в localStorage
  и поднимутся сами при следующем инжекте.
- Явный сброс («Как у Claude») переживает возврат: он лежит как `"none"`, а не как отсутствие слоя.

Два случая, когда страница **сливает, но не красит** (экран трогать нельзя): `themeState.previewing` (идёт примерка
мышью) и `liveState.on` (крутятся живые цвета, `:2259`). Обработчик стоит в `onCommand` рядом с `status`/`live-colors`,
**до** отмены примерки (`:4523`), иначе приезд команды гасил бы подменю под рукой у Элвиса.

### 5. Когда приложение шлёт `themes-restore`

Понятие **поколения**: старт приложения (`ClaudeAXController.start()`, п. 19) или смена pid Claude
(`ClaudeApp.onRestart`, п. 18). В одном поколении — не больше **трёх** команд:

1. первый тик поколения, где Claude вообще есть на экране (`paintableTitles()` непуст, п. 20);
2. дальше — когда **набор заголовков окон Claude изменился** (окно открылось/закрылось/переименовалось),
   но не чаще одного раза в **5 с** и не больше трёх раз за поколение.

Признак нарочно взят из AX-заголовков, а не из `status.json`: тот весит ~1 МБ и уже разбирается на каждом тике
(п. 24) — второго читателя ему не надо.

Почему три: после переустановки страницы поднимаются не разом, и инжект в них приезжает позже команды. Окно,
открытое потом, читает уже долитую карту из localStorage само (`restoreTheme` при инжекте) — досылать ему нечего.
Больше трёх раз за поколение — это шторм, а не восстановление.

Файл пуст (никто ничего не выбирал) — команд нет вовсе. Claude не запущен — тоже.

### 6. Ключ по id чата

Внутри `inject.js` (раздел 2а) ключи разводятся явно, поверх `myChatId()` из WF29 (п. 25):

- `chatIdKey()` → **`if (!themable) return null;`** первой строкой, дальше `id:<myChatId()>` либо `null`.
  Проверка `themable` обязана стоять явно: на неё опирается `tests/theme-store.test.mjs:149-152`
  («чужая страница ключей не даёт вовсе» — `chatKey`, `sessionKey`, `themeKey` все три `null`). Сегодня чужую
  страницу спасает только то, что `newWindowSessionId` требует префикса `local_` (`:3707-3710`); у WF29 функция
  другая (`myChatId`), её гарантий план WF29 не оговаривает — значит гарантию ставим у себя;
- `chatTitleKey()` → нынешний `chat:<заголовок>` (заглушки по-прежнему ключом не становятся, `:810`);
- `chatKey()` → **`chatIdKey() ?? chatTitleKey()`** — «действующий ключ чата», его же отдаёт `status().chatKey`;
- `chatEntry(map)` → `mapEntry(map, chatIdKey()) ?? mapEntry(map, chatTitleKey())`; им заменяются три места чтения
  (`restoreTheme` `:1099`, `storedLayer` `:1125`, `applyChatEntry` `:1209`);
- `writeKeys()` (`:1161`) → `[chatIdKey?, chatTitleKey?, main?]` — пока id известен, **пишем оба ключа**: id главный,
  заголовок — тень для окон, которые id ещё не знают.

Приоритет по слою: `id:` → `chat:` → сессия → `main` → `*`.

**Мелочь, без которой окна разово моргнут** (п. 6): `sameSessionKey` (`:894`) сверяет сохранённый ключ сессии с
`chatKey()`. Теперь он обязан принимать **и `chatIdKey()`, и `chatTitleKey()`** — иначе сессии, записанные до
обновления, перестанут признаваться своими.

Заголовок-заглушка при известном id ключом чата теперь **становится** (через `id:`) — осознанная смена поведения:
у безымянного чата есть id, и выбранный в нём цвет обязан остаться, когда имя появится. `main` при этом пишется
как раньше, поэтому «новый чат цвет окна не меняет» сохраняется.

Что это чинит: переименование чата (id не меняется — пункт 20) и два чата с одинаковым именем, открытых
одновременно (у каждого свой `id:`).

Чего это **не** чинит и где даже подпортит (находка критика, проверено): «чужой цвет по совпадению заголовков»
из этого списка **убран**. `migrateChatKey` копирует запись ПО ЗАГОЛОВКУ, поэтому новый чат, которому достался
освободившийся заголовок переименованного старого, унаследует его цвет — и теперь закрепит на своём `id:`.
Сегодня это временная осечка, которая проходит после переименования; после WF35 она становится постоянной.
Ловить её картой чатов WF29 (`window.__myclaude.chats`, «переносим, только если у заголовка ровно один кандидат»)
в WF35 не будем: карта приезжает с задержкой в секунды, а перенос обязан сработать в момент инжекта — иначе
окно моргнёт серым. Цена ошибки — один чат не того цвета, лечится выбором темы. Записано риском 11.

### 7. Перенос старых записей: копия, без удаления, и не только при инжекте

`migrateChatKey()`: id известен, записи `id:<…>` ещё нет, а запись по заголовку есть (в том числе легаси `w:`,
через `mapEntry` `:882`) — **копируем её в `id:<…>` и оставляем старую на месте**.

Зовётся в **трёх** местах:

1. при инжекте, перед `restoreTheme()` (`:1374`);
2. в `syncChatTheme` (`:1216`) до `applyChatEntry` — **обязательный второй вызов**: у попапа id появляется
   позже инжекта (п. 26), и без него перенос в попапе не случился бы никогда;
3. **первой строкой `writeLayers` (`:1168`), перед записью** — обязательный третий (находка критика).
   Причина: `setMapLayers` начинает с `const entry = mapEntry(map, key) ?? {}` (`:1141`), а `chatEntry`
   читает `id:` РАНЬШЕ `chat:`. Если команда `theme` придёт в окно, где переноса ещё не было (попап
   в первые секунды, п. 26), запись `id:` создастся с ОДНИМ слоем и навсегда закроет более полную тень
   `chat:` — остальные слои чата (шрифт, размер, рамка) пропадут с экрана. Перенос перед записью это
   исключает: `id:` стартует с копии полной записи.

Почему не удаляем старую запись: по ней ещё живёт окно, которое своего id не знает (попап в первые секунды,
непропатченная страница). Ключ безвреден — `id:` сильнее — и уйдёт вытеснением на стороне файла.
Уборку карты страницы WF35 не делает (см. «Не делаем»).

### 8. Хвосты той же переустановки — два довеска по строке

- **`ProjectPaint.forget()`**: на `ClaudeApp.onRestart` (там уже висит `menu.clearCache()`, `ClaudeAXController.swift:51`)
  сбрасываем отпечатки `marks` **без команд снятия** — в отличие от приватного `clear()` (`ProjectPaint.swift:159`),
  который ещё и шлёт. Ближайший тик перекрасит окна проектов заново. Без этого цвет проекта после переустановки
  не вернётся, пока не перезапустят приложение (п. 21) — ровно это Элвис и наблюдал.
- **Живые цвета**: на том же `onRestart` дёргаем `actions.resendLiveColors()` (п. 19) — сегодня она есть только
  в `start()`. Крутёж тоже жил в localStorage.

**Как это проверяется — честно.** `onRestart` висит на смене pid **именно Claude** (`ClaudeApp.swift:69`),
поэтому перезапуск ПРИЛОЖЕНИЯ его не вызывает вовсе: `pkill` Пимпа открывает новое поколение через
`ClaudeAXController.start()` (`:116`), но `onRestart` при этом молчит. Значит решение 8 живым гейтом
**не закрывается** — только Swift-тестами 28 и 30 плюс одним ручным перезапуском Claude, который делает Элвис
(это закрывает чат оркестратора). Шаг 9 гейта переписан соответственно, в run-файл идёт строка
«решение 8 закрыто тестами 28/30; живой перезапуск Claude — на Элвисе».

Хорошая новость, проверенная по коду: `lastPID` присваивается только внутри `if let found = found`
(`ClaudeApp.swift:52-71`) — пока Claude отсутствует, прошлый pid сохраняется. Значит после переустановки
и «Поставить» `onRestart` действительно сработает, и механика решения 5 держится.

### 9. Диагностика (не интерфейс)

- `status().restore = {at, keys, merged, painted}` — когда приезжала команда, сколько ключей приняли, сколько слоёв
  долили, красились ли. Плюс `status().chatKey` уже есть, `status().chat` даёт WF29.
- Строка `statusText` приложения получает кусок `themes=<ключей в файле>/<команд в поколении>`.
- **`status().raw` меняет смысл, кода не меняя**: он считается по `themeKey()` (`inject.js:4794`), а тот теперь
  отдаёт `id:…` — значит на гейте в `raw` будет запись по id, а не по заголовку (запись `chat:` смотреть через
  `rawMain`-соседа или прямым чтением карты). Назвать это в шаге 1 гейта и в `docs/CHECKLIST.md` (батч D),
  иначе первый же читатель решит, что тень не пишется.

### 10. Позиции окон по id — отдельно, не в WF35

Хранить позицию дёшево, **возвращать — нет**: надо знать, какое окно каким чатом занято в момент подъёма Claude
(а это карта WF29, живущая с задержкой), двигать окно через AX и не подраться при этом с «Расставить» и будущими
раскладками. Владелец геометрии — **WF21** (#5393 сетки, #5397 окна местами, #5398 раскладка проектов); в марафоне
05.09 пункт «память позиций/спрятать все» (#5385) Элвис **отдельно отклонил**
(`docs/run-marathon-2026-09-05.json`, `declined`).

1. **До WF35 по тем же файлам пройдут ЧЕТЫРЕ воркфлоу — WF29, WF34, WF31, WF30.** `claude-patch/inject.js`

   Смягчение: ветка от `main` **после слияния WF30** (шапка), а не после WF29; номера строк в плане — ориентир,
   исполнитель ищет по именам функций; ожидание от WF29 — ровно одна функция `myChatId()` и поле `chat` в команде
   (пп. 25, 27). Названия разошлись — зовём то, что есть, и пишем в отчёт: разница в одну строку.
   Отдельно батчу A: перед правкой `onCommand` перечитать, как WF31 расставил примерку, — обработчик
   `themes-restore` обязан встать ДО отмены примерки в той редакции, которая будет на диске, а не в этой.
2. **Зеркало и страница разойдутся в ключах** (решение 2 повторяет `writeKeys` на стороне Swift). Цена ошибки —
   окно вернётся серым, а не чужого цвета: возврат доливает только пустые слои. Держат тест 21 и **самолечение
   решением 3**: первый же ответ probe перепишет файл картой страницы. Батч V проверяет расхождение отдельным пунктом.
3. **Команда не застанет страницу.** Инжект приезжает позже команды — отсюда три попытки на поколение. Если Claude
   поднимается дольше ~40 с, окно останется серым до следующего поколения (перезапуск приложения). Единственный
   сценарий, где Элвису снова придётся что-то сделать руками.
4. **Probe занят гейтом — файл не обновляется.** По правилу WF29 приложение молчит 60 с и пробует снова; пока
   молчит, файл живёт зеркалом (решение 2), то есть не деградирует, а лишь не догоняет чужие правки. Забыли удалить
   `probe.js` после гейта — приложение молчит бесконечно; поэтому шаг 11 гейта заканчивается удалением файла,
   и это же записано в `docs/CHECKLIST.md` (батч D).
5. **Раздувание карты**: с двумя ключами на чат карта страницы растёт вдвое, у localStorage потолка нет. У файла
   потолок 120 ключей есть. Уборку карты страницы WF35 не делает — если распухнет, отдельная задача.
6. **«Снял всё» и «потерял localStorage» различаются только моментом в поколении** (решение 3, переписано после
   критика — прежняя формулировка «практически недостижимо» была неверна: `scope:"all"` с `theme:null` доходит
   до нуля ключей за два клика, `inject.js:1334-1351` + `:838-843`). Теперь пустой ответ считается правдой везде,
   кроме ПЕРВОГО ответа поколения. Остаточный риск сузился до одного сценария: Claude перезапустился, приложение
   ещё не получило ни одного ответа, и ровно в это окно Элвис жмёт «Как у Claude (все окна)» — тогда снятое
   вернётся один раз. Лечится вторым нажатием.
7. **`ProjectPaint.forget()` на перезапуске Claude даст залп команд**: окон много — покраска пойдёт по тику через
   очередь 0,6 с, в худшем случае десяток команд за 6 с. Приемлемо, но на гейте посмотреть глазами (шаг 9):
   мигает — ограничить одним окном на тик отдельной задачей.
8. **Слияние идёт в нескольких окнах одновременно**: команда `scope:"all"` приходит во все страницы, каждая пишет
   общий localStorage. Результат детерминирован и одинаков, поэтому расхождения не будет; теоретическая гонка —
   выбор темы ровно в ту же миллисекунду — потеряет один выбор, который приложение всё равно записало в файл.
9. **Тесты по умолчанию сидят на `local_test`** (п. 31). Ожидания правятся ровно в двух проверках (список выше);
   покраснело что-то ещё — значит модель ключей задета глубже, чем считает план: остановиться и звать гейт,
   а не подгонять ожидания.
10. **`status.json` и лоадер** WF35 не читает и не трогает вовсе — риск смены лоадера (WF26/WF27) на этот воркфлоу
    не распространяется. Это следствие решения 5 (признак — AX-заголовки).
11. **Освободившийся заголовок закрепляет чужой цвет насовсем** (решение 6, находка критика). Старый чат
    переименовали, новый получил его прежнее имя → `migrateChatKey` скопирует запись по заголовку на `id:` нового
    чата. Сегодня это временная осечка (проходит после переименования), после WF35 — постоянная. Это ухудшение
    существующей осечки, а не новая поломка; цена — один чат не того цвета, лечится выбором темы. Если начнёт
    мешать — отдельной задачей: переносить только когда карта чатов WF29 знает у заголовка ровно одного кандидата.
12. **Поле `themes` шлёт только главное окно** (решение 3). Если у Элвиса вообще нет открытой страницы
    `claude.ai` (все окна — попапы `about:blank`), файл перестанет догонять правду и будет жить одним зеркалом.
    На практике главное окно есть всегда — оно и открывает попапы; в `docs/CHECKLIST.md` (батч D) это названо

13. **Тень `chat:<заголовок>` протухает при переименовании**: новая тень пишется только следующим выбором темы,
    поэтому окно, которое своего id ещё не знает (попап в первые секунды, решение 2), после переименования
    несколько секунд остаётся некрашеным. Допустимо; решение 2 обещает чуть больше, чем даёт, — записано здесь,
